# sitekit

Two small tools for a **catalog-driven static site**: a generator that turns a
JSON catalog into a page plus its text route, and a browser-driven audit gate
that checks the built page actually works.

No package manager. The builder is Node with built-ins only (`node:fs`,
`node:path`); the audit uses the Python standard library plus Playwright, which
it already needed where it came from.

Extracted from the [mariyaholic room](https://github.com/mariyaholic/mariyaholic),
where both were hardwired to that one site.

| File | What |
|---|---|
| [`build.mjs`](build.mjs) | catalog → `index.html` + `catalog.md`; validates the catalog; `--check` for CI |
| [`audit.py`](audit.py) | serves the site, drives it headless, checks the interactions; JSON report |
| [`audit.config.json`](audit.config.json) | the default audit config (selectors, viewports, token checks) |
| [`catalog.schema.json`](catalog.schema.json) | the room's schema, kept as a worked example — point `--schema` at your own |

Requires Node ≥ 22, Python ≥ 3.13, and (for the audit) Playwright with a
Chromium/Edge/Chrome channel installed.

## build.mjs

```sh
node build.mjs [--root DIR] [--site DIR] [--schema FILE] [--generator NAME]
               [--check] [--no-validate] [--help]
```

| Flag | Meaning |
|---|---|
| `--root DIR` | directory holding `catalog.json` (default: the current directory) |
| `--site DIR` | directory holding `src/` and `index.html` (default: `<root>/site`) |
| `--schema FILE` | JSON Schema for the catalog (default: `<site>/catalog.schema.json`) |
| `--generator NAME` | the name written into the "generated by" notes (default `site/build.mjs`) |
| `--check` | write nothing; exit non-zero if the committed output is stale |
| `--no-validate` | skip schema validation |

It reads `src/room.css`, `src/room.js` and `src/room.svg` from the site
directory and writes `<site>/index.html` plus `<root>/catalog.md`.

**The defaults reproduce the room byte-for-byte.** Running `node build.mjs` from
the room root gives the same `index.html` and `catalog.md` as the original
`site/build.mjs`, which is what `--generator` defaults to. Change `--generator`
(and `--root`/`--site`) and the same tool serves any layout.

Validation covers the JSON Schema subset the room's schema uses — `type`,
`required`, `properties`, `items`, `enum`, `pattern`. Other keywords are ignored
rather than guessed at. Failures name each offending path:

```
catalog.json does not match site/catalog.schema.json:
  catalog.objects[0].id: "Bad_ID" does not match ^[a-z][a-z0-9-]*$
  catalog.objects[0].tools[0].status: "broken" is not one of shipped, beta, planned, retired
```

`--check` is the CI gate:

```
$ node build.mjs --check          # fresh
up to date — 9 objects, 6 tools
$ node build.mjs --check          # after editing catalog.json without rebuilding
stale output — run the builder and commit the result:
  site/index.html
  catalog.md
```

Exit codes: `0` success, `1` validation failure or stale output, `2` bad usage.

## audit.py

```sh
python audit.py [--config FILE] [--root DIR] [--site DIR] [--catalog FILE]
                [--port N] [--shots] [--json PATH] [--help]
```

**Expectations come from the catalog, not from the tool.** The hotspot count is
the number of objects, the notebook row count is the total tools, the section
headings are the object names, and the chapter/tool it opens (plus the deep link
it restores) are picked from the catalog. Change the catalog and the audit
follows; there are no hardcoded counts or ids left.

What the catalog cannot supply comes from the **config file**. `audit.config.json`
is loaded automatically if it sits next to `audit.py`; `--config FILE` merges
over it; CLI flags win over both.

```json
{
  "siteDir": "site",
  "catalog": "catalog.json",
  "page": "index.html",
  "viewports": [375, 1440],
  "viewportHeight": 900,
  "port": 0,
  "shots": false,
  "selectors": {
    "stage": ".stage svg",
    "hotspot": ".spot",
    "notebookRow": ".row",
    "notebookSection": ".notebook .chapter",
    "notebookHeading": ".notebook .chapter h3",
    "window": "#win",
    "windowTitle": "#win-title",
    "toolCard": ".card[data-tool]",
    "toolSpec": "#win-tools .spec",
    "backButton": "#win-acts button",
    "hiddenCheck": [".spot", ".notebook", ".masthead"],
    "reducedMotionMarker": ".lamp-glow"
  },
  "reducedMotion": { "requiredOpacity": 1.0 },
  "tokenChecks": { "--lamp": "#bb9955" }
}
```

`tokenChecks` maps a CSS custom property to its expected value; a mismatch fails
the run. That is the guard against a silently broken token layer:

```
FAIL
  375: token --lamp = '#ff0000', want '#bb9955'
  1440: token --lamp = '#ff0000', want '#bb9955'
```

Checks, per viewport: no console/page errors, no horizontal overflow, correct
hotspot/row/section counts, every catalog name has a notebook heading, the
hotspot → window → tool → back interaction, a reopened tool does not duplicate
its spec, `Escape` closes, a deep link restores its tool, keyboard reach, and
the token values. Then, once, under `prefers-reduced-motion`: no core element
hidden and the marker at its end state.

One browser is launched per run and reused across viewports via contexts, rather
than the three launches-per-run the original did.

### Report shape

`--json PATH` writes the full report; the same data drives the console summary.

```json
{
  "ok": true,
  "url": "http://127.0.0.1:53321/index.html",
  "catalog": "catalog.json",
  "siteDir": "site",
  "expected": { "hotspots": 9, "rows": 6, "sections": 9, "names": ["Quality of Life", "..."] },
  "exercise": {
    "chapter_id": "qol", "chapter_name": "Quality of Life", "tool_name": "Desk Reset",
    "deep_chapter_id": "looks", "deep_tool_id": "mh-look-001", "deep_tool_name": "Nocturne Shell"
  },
  "tokenChecks": { "--lamp": "#bb9955" },
  "viewports": [
    {
      "width": 375, "height": 900,
      "hotspots": 9, "rows": 6, "sections": 9,
      "overflow": 0, "focus": "motion",
      "tokens": { "--lamp": "#bb9955" },
      "failures": []
    }
  ],
  "reducedMotion": {
    "hidden": 0, "marker": ".lamp-glow", "opacity": "1", "requiredOpacity": 1.0, "failures": []
  },
  "failures": [],
  "notes": ["375: 9 hotspots, 6 rows, 9 sections, overflow 0px, focus -> 'motion'"]
}
```

Exit codes: `0` all checks green, `1` at least one failure, `2` bad usage.

## Worked example

Both tools run against the room that they came from, from the room's root:

```sh
cd /path/to/mariyaholic
node /path/to/sitekit/build.mjs --check     # up to date — 9 objects, 6 tools
python /path/to/sitekit/audit.py            # PASS — all checks green
```

Note that `--root` defaults to the *current directory*, not the tool's own
directory, so the tools are run from the repo they are checking.

## Limits

- Asset names inside the site directory are fixed at `src/room.css`,
  `src/room.js` and `src/room.svg`; the config parameterizes paths and selectors,
  not those filenames.
- The audit drives a specific markup contract (`.spot[data-object]`, `#win`,
  `.card[data-tool]`, `#win-tools .spec`). A site with different markup needs a
  config with its own selectors.
- The schema validator implements a subset, not draft 2020-12 in full.
- The audit needs a real browser; if Playwright or a Chromium channel is
  missing it exits with a clear message rather than reporting success.
